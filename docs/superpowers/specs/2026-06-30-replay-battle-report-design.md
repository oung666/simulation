# 回放录制与战绩系统设计

## 目标

为当前仿真项目增加一套轻量但完整的“回放录制 + 战绩浏览 + 回放查看”功能，满足多次批量仿真后的复盘需求。

第一版需要让用户能够：

- 在顶部工具栏控制是否开启录制
- 在仿真自然结束时自动结算
- 在仿真过程中手动提前结算
- 为每一局已录制仿真生成一条完整战绩
- 在独立的 `战绩` 对话框中浏览历史战绩
- 从战绩中打开对应回放
- 只清理战绩记录，或连同回放文件一起彻底删除

本设计必须注意架构边界，不能把录制、战绩统计、存储、回放播放都继续堆进 `MainWindow` 或 `MapCanvas`。

## 已确认的产品决策

- 顶部工具栏新增 `录制` 开关
- 顶部工具栏新增 `结算` 按钮
- 顶部工具栏新增 `战绩` 按钮
- `战绩` 按钮打开独立对话框
- 战绩页采用完整赛后页形式：阵营总览 + 单位明细 + 关键事件 + 回放入口
- 结算支持两种方式：
  - 仿真自然结束后自动结算
  - 用户点击工具栏 `结算` 手动结算
- 回放录制采用 `快照 + 事件流`
- 默认快照间隔为 `2.5 秒`
- 关键战斗节点额外补一份快照
- 回放播放使用独立可视化界面，不直接复用主界面
- 回放界面尽量复用现有地图渲染能力，但不能和实时仿真共用同一套运行状态
- 清理分为两级：
  - `清除战绩记录`
  - `彻底删除战绩+回放`

## 范围

### 本次要做

- 工具栏录制开关
- 工具栏手动结算
- 工具栏战绩入口
- 回放文件生成
- 战绩摘要生成
- 历史战绩浏览界面
- 完整赛后页
- 独立回放查看器
- 战绩清理与回放删除
- 支持多局仿真后的轻量存储和索引

### 本次不做

- 视频导出
- 高级时间轴编辑
- 复杂图表分析
- 多局对比分析页
- 联网同步回放
- 用回放界面替换现有实时仿真主界面

## 用户视角的产品流程

### 1. 录制

顶部工具栏新增三个控件：

- `录制`：拨码式开关
- `结算`：手动提前结算
- `战绩`：打开历史战绩

行为如下：

- `录制` 关闭时，仿真照常运行，但不会写入回放和战绩
- `录制` 开启时，为当前这局仿真创建一个录制会话
- 录制会话在启动时立即保存开局状态
- 仿真运行过程中按固定间隔写快照，并持续记录关键事件

### 2. 结算

结算有两种入口：

- 仿真自然结束后自动结算
- 用户点击工具栏 `结算` 后手动结算

两种结算最终都要生成：

- 一份完整回放文件
- 一份轻量战绩摘要
- 一条用户可见的“已生成战绩”状态提示

手动结算需要记录结算原因，例如 `manual_settlement`，用于后续区分自然结束和人工结束。

### 3. 战绩对话框

点击工具栏 `战绩` 后，打开独立 `QDialog`。

布局分为左右两栏：

- 左侧：历史战绩列表
- 右侧：当前选中战绩的完整赛后页

左侧列表每行显示一局：

- 结算时间
- 场景名
- 胜负结果
- 仿真时长
- 蓝红双方剩余单位数
- 是否存在回放

右侧赛后页包含：

- 头部卡片：场景、结束时间、结果、时长、是否有回放
- 阵营总览卡片：
  - 蓝方存活
  - 蓝方损失
  - 蓝方发射数
  - 蓝方命中数
  - 红方存活
  - 红方损失
  - 红方发射数
  - 红方命中数
- 单位明细表：
  - 阵营
  - 单位名称
  - 型号 / 类型
  - 存活状态
  - 击毁数
  - 是否被摧毁
  - 发射数
  - 命中数
  - 最终位置
  - 最终任务状态
- 关键事件列表：
  - 首次探测
  - 首次发射
  - 首次击毁
  - 任务完成
  - 一方崩盘 / 全灭
  - 仿真结束
- 底部操作区：
  - `查看回放`
  - `跳转关键事件`
  - `清除战绩记录`
  - `彻底删除战绩+回放`

### 4. 回放查看器

回放播放使用独立界面，不直接复用实时仿真主窗口。

第一版控制项：

- 播放
- 暂停
- 倍速切换（`1x`、`2x`、`4x`）
- 关键事件跳转

第一版暂不追求：

- 自由拖动时间轴
- 逐帧精细回放
- 高级观战镜头系统

第一版的目标是“可用、可复盘、可跳转关键片段”，而不是完整编辑器。

## 技术架构

为了避免继续扩大 `ui/main_window.py` 的职责，建议新增独立的 `replay` 模块目录。

### 新增模块

- `simulation/replay/models.py`
  - 回放与战绩相关的数据结构
- `simulation/replay/recorder.py`
  - 录制器，会话开始、快照采集、事件收集、结束封存
- `simulation/replay/results.py`
  - 战绩统计与赛后页数据构建
- `simulation/replay/storage.py`
  - 回放文件、战绩摘要的读写、加载、删除、索引
- `simulation/replay/runtime.py`
  - 回放运行时，负责从快照恢复并按时间推进
- `simulation/ui/battle_report_dialog.py`
  - 历史战绩列表与赛后页
- `simulation/ui/replay_viewer_dialog.py`
  - 回放播放界面

### 现有模块只做轻量接入

- `simulation/ui/main_window.py`
  - 增加工具栏按钮
  - 打开战绩对话框 / 回放对话框
  - 触发结算
- `simulation/ui/map_canvas.py`
  - 在实时仿真 tick 中向录制器提供当前战场状态
  - 继续作为实时模式地图画布
- `simulation/controllers/combat_controller.py`
  - 继续负责战斗事件生成
  - 必要时增加更结构化的事件输出
  - 不直接负责战绩 UI 和存储

## 数据模型

建议使用两层持久化：

- 一层是完整回放文件
- 一层是轻量战绩摘要

这样历史战绩列表无需每次都加载大回放文件。

### 完整回放：`ReplayRecord`

这是回放播放所需的完整数据。

建议字段：

- `replay_id`
- `scenario_name`
- `started_at`
- `ended_at`
- `settlement_reason`
- `duration_seconds`
- `tick_interval_seconds`
- `snapshot_interval_seconds`
- `participants`
- `initial_state`
- `snapshots`
- `event_stream`
- `highlights`
- `final_state`

#### 快照：`ReplaySnapshot`

每个快照要能支撑“从这一时刻恢复回放状态”，不依赖实时仿真控制器继续推演。

建议内容：

- `time`
- `clock_state`
- `unit_states`
- `flying_weapon_states`
- `mission_states`
- `contact_track_states`
- 视角或显示状态（如果回放表现层需要）

每个单位状态至少包括：

- `unit_id`
- `name`
- `side`
- `unit_type`
- `class_name`
- `alive`
- `position`
- `heading`
- `speed`
- `fuel`
- `weapon_inventory`
- `target_id`
- `motion`
- `route_points`

#### 事件流：`ReplayEvent`

用于描述快照之间发生了什么。

第一版建议记录这些事件类型：

- `detected`
- `shared_contact`
- `launched`
- `hit`
- `miss`
- `expired`
- `unit_destroyed`
- `mission_completed`
- `simulation_finished`
- `manual_settlement`

每个事件建议包含：

- `time`
- `event_type`
- `source_id`
- `target_id`
- `weapon_class`
- `position`
- `message`
- 可选数值字段，例如距离、命中率、探测距离

### 轻量战绩：`BattleReportSummary`

这是战绩列表与赛后页优先读取的数据。

建议字段：

- `report_id`
- `replay_id`
- `scenario_name`
- `finished_at`
- `settlement_reason`
- `winner_side`
- `result_label`
- `duration_seconds`
- `replay_path`
- `has_replay`
- `side_summary`
- `unit_rows`
- `highlights`

#### 阵营总览：`SideSummary`

每个阵营统计：

- `alive_count`
- `lost_count`
- `launch_count`
- `hit_count`
- `kill_count`

#### 单位战绩行：`UnitBattleRow`

每个单位统计：

- `unit_id`
- `name`
- `side`
- `unit_type`
- `class_name`
- `alive`
- `kills`
- `destroyed`
- `launches`
- `hits`
- `last_position`
- `final_mission_status`

## 存储布局

建议分开两个目录：

- `simulation/data/replays/`
- `simulation/data/battle_reports/`

规则如下：

- 完整回放写入 `replays`
- 轻量战绩摘要写入 `battle_reports`
- 战绩浏览器只扫描 `battle_reports`
- 只有用户点击 `查看回放` 时，才加载 `replays` 中对应文件

建议命名方式：

- 回放文件：`<timestamp>-<replay_id>.json`
- 战绩文件：`<timestamp>-<report_id>.json`

战绩摘要中保留：

- `replay_id`
- `replay_path`

这样后续打开、删除、校验都更明确。

## 录制策略

### 定时快照

- 固定间隔：`2.5 秒`
- 开始录制时立即保存初始快照
- 结算时强制保存最终快照

### 关键事件补快照

在这些节点额外补一份快照：

- 本局首次探测
- 本局首次发射
- 任意命中事件
- 任意单位被摧毁
- 任意任务完成
- 仿真结束
- 手动结算

### 为什么这样设计

- `2.5 秒` 比 `5 秒` 能明显提升回放连贯性
- 关键节点补快照能减少“跳过去看不到关键片段”的问题
- 相比更高频快照，文件体积仍然可控，适合多局批量仿真

## 结算与结果生成逻辑

### 自动结算

当仿真自然达到结束条件时触发。

流程：

- 停止当前录制会话
- 强制写入最终快照
- 生成战绩摘要
- 保存回放文件与战绩摘要
- 给出成功提示

### 手动结算

用户点击工具栏 `结算` 时触发。

流程：

- 停止当前录制会话
- 强制写入最终快照
- 标记 `manual_settlement`
- 基于当前战场状态生成战绩
- 保存回放文件与战绩摘要
- 给出成功提示

第一版不应该因为“尚未自然结束”就丢弃这局已经录下的内容。

## 回放运行时设计

回放不能直接驱动实时 `CombatController` 继续跑。

回放运行时的职责应该是：

1. 读取回放文件
2. 找到合适的起始快照
3. 恢复回放状态
4. 将事件流推进到目标时间
5. 用“回放状态”驱动界面显示

这意味着要明确分开两种模式：

- `LiveMode`：实时仿真
- `ReplayMode`：回放浏览

这是本设计最重要的架构原则之一。

## 清理策略

必须支持两级删除。

### 只清理战绩记录

动作：`清除战绩记录`

行为：

- 只删除 `battle_reports` 中对应摘要文件
- 保留 `replays` 中原始回放文件

适用场景：

- 用户只想清空战绩列表
- 但回放文件仍想保留备查

### 同时删除战绩和回放

动作：`彻底删除战绩+回放`

行为：

- 删除战绩摘要
- 删除其对应回放文件
- 删除后立即刷新列表

适用场景：

- 批量仿真文件太多，需要真正清磁盘

### 批量删除

第一版建议同时支持：

- `清除全部战绩记录`
- `彻底删除全部战绩+回放`

这两类危险操作都需要确认弹窗，并显示受影响的记录数，必要时显示将被删除的回放文件数。

## 异常处理

### 未开启录制

- 如果用户没有开启录制，则结算时不生成回放和战绩
- UI 明确提示“当前未开启录制”

### 写入失败

- 如果回放写成功但战绩写失败，要提示异常，并保留回放路径信息
- 如果战绩写成功但回放写失败，要把 `has_replay` 标成 `false`
- 文件写入尽量采用原子写方式，避免生成损坏 JSON

### 回放文件丢失

- 如果战绩还在，但对应回放文件缺失，则 `查看回放` 按钮置灰并给出提示

### 删除安全

- 只删战绩时，不能误删无关回放文件
- 删回放时，必须校验目标路径确实属于回放目录

## 分阶段建议

### 第一阶段

- 工具栏入口
- 录制会话
- 回放文件写入
- 战绩摘要生成
- 战绩对话框
- 回放查看器（播放 / 暂停 / 倍速 / 关键事件跳转）
- 两级清理

### 第二阶段

- 更丰富的筛选
- 更强的回放控制
- 更密集的分析能力
- 更成熟的高光片段和批量对比

## 对当前代码库的特别要求

- 回放代码尽量放在 `replay/` 目录下，不继续塞进 `MainWindow`
- 战绩统计逻辑不要放进 `CombatController`
- 回放运行时必须与实时仿真 tick 解耦
- 优先拆成小模块，而不是继续增肥已有大文件
- 界面视觉和绘制风格可以复用，但运行状态绝不能复用成一锅

## 验收标准

第一版完成的标准是：

- 用户可以在工具栏控制是否录制
- 一局已录制仿真能自动结算，也能手动结算
- 结算后能生成一条战绩记录
- `战绩` 对话框能高效浏览多条历史战绩
- 选中某条战绩后能看到完整赛后页
- 用户可以从战绩中打开对应回放
- 用户可以只清除战绩摘要
- 用户也可以彻底删除战绩和回放
- 实现过程中没有明显继续膨胀实时主界面控制类
